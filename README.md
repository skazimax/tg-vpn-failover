# TG VPN Failover

Независимый системный слой исходящего доступа к Telegram для серверов, где прямое соединение недоступно.

Сервисы-потребители ничего не знают об AdGuard или VLESS. Они используют одну постоянную точку входа:

```text
socks5h://127.0.0.1:1079
```

Схема:

```text
mtg / Telegram bot / другой сервис
              |
              v
       SOCKS5 127.0.0.1:1079
              |
       mtproxy-egress (sing-box)
          /               \
 AdGuard :1080       VLESS auto :1081
                         |
             URLTest по Auto (gRPC)
             fallback: Auto, затем Auto+
```

## Поведение

- Начальный маршрут новой установки — AdGuard. Выбранный маршрут сохраняется в конфигурации общего SOCKS; исправный VLESS автоматически на AdGuard не возвращается.
- Примерно каждые 30 секунд проверяются общий SOCKS `1079`, AdGuard `1080` и VLESS `1081`. Для каждого проверяются `core.telegram.org/getProxyConfig` и ответ Bot API на `getMe` с заведомо недействительным токеном. Действующий токен не требуется, сообщения не отправляются.
- После трёх последовательных ошибок активного upstream контроллер проверяет резерв и меняет маршрут. Исправный резерв перед переключением не перезапускается.
- Если upstream исправен, а общий SOCKS не проходит проверку, контроллер перезапускает только общий egress, сохраняя VPN-маршрут. Неисправный резерв фиксируется в health-данных и журнале, даже когда основной канал работает.
- VLESS предпочитает записи `Авто` с транспортом gRPC из первой подписки и выбирает доступную через `urltest`. Если gRPC отсутствует, используются остальные записи `Авто`; если нет обычной группы `Авто`, используется `Авто+`. Это выбор по составу подписки, а не автоматический переход между группами при сетевой ошибке.
- Первая непустая строка `/etc/mtproxy-failover/subscriptions` — основной URL подписки. Остальные строки не используются автоматически.
- Подписка обновляется каждые 6 часов. До применения выполняются `sing-box check` и проверка Telegram через отдельный процесс sing-box на случайном localhost-порту под пользователем `mtproxy-vless`.
- Применение подписки и переключение используют общую блокировку. Скачивание подписки и предварительная проверка выполняются вне неё; параллельные обновляющие процессы ограничены отдельной блокировкой.
- Конфигурация заменяется атомарно, затем проверяется рабочий порт. При ошибке восстанавливается предыдущая версия. Журнал незавершённой операции позволяет следующему запуску завершить откат после аварийного завершения процесса или перезагрузки.
- Одинаковый набор узлов, другое их расположение в подписке или дубликаты не приводят к перезапуску VLESS. При выборе другого узла URLTest существующие входящие соединения сохраняются (`interrupt_exist_connections=false`). Реальная смена upstream по-прежнему перезапускает общий egress и может кратко разорвать соединения.

## Состав репозитория

- `lib/controller.py` — общий контроллер: проверки, преобразование подписки, переключение и откат;
- `scripts/mtproxy-vless-update` — точка запуска обновления подписки;
- `scripts/mtproxy-failover` — точка запуска health-check и переключения;
- `scripts/tg-vpn-failover-status` — одна компактная строка `VPN: AdGuard/SKIPP` для CLI или управляющего бота;
- `systemd/` — службы и таймеры;
- `config/mtproxy-egress.json` — начальный маршрут через AdGuard;
- `config/egg-cam-control-proxy.conf` — пример настройки потребителя;
- `config/mtg-egress.conf` — необязательное упорядочивание запуска `mtg`.

Секреты и URL подписок в репозиторий не добавляются.

## Подключение потребителя

Для приложения, поддерживающего стандартные proxy-переменные:

```ini
[Service]
Environment=ALL_PROXY=socks5h://127.0.0.1:1079
Environment=all_proxy=socks5h://127.0.0.1:1079
```

Для `mtg`:

```toml
[network]
proxies = ["socks5://127.0.0.1:1079"]
```

Потребитель не должен зависеть от `egg-cam-adguard.service` или управлять переключением самостоятельно. Если общая точка временно недоступна, приложение должно повторять сетевой запрос.

## Проверка

```bash
curl -4 --fail --silent --show-error \
  --proxy socks5h://127.0.0.1:1079 \
  --max-time 20 https://core.telegram.org/getProxyConfig

systemctl is-active mtproxy-egress.service mtproxy-vless.service
systemctl is-active mtproxy-failover.timer mtproxy-vless-update.timer
sudo cat /run/mtproxy-failover/state
sudo cat /run/mtproxy-failover/failures
sudo cat /run/mtproxy-failover/health.json
sudo journalctl -t mtproxy-failover -n 50 --no-pager
/usr/local/sbin/tg-vpn-failover-status
python3 -m unittest discover -s tests
```

Контролируемое ручное переключение для проверки или обслуживания:

```bash
sudo /usr/local/sbin/mtproxy-failover --force-switch
```

Перед изменением общей точки контроллер проверяет доступ к Telegram через
целевой upstream. Если резервный маршрут не работает, переключение отменяется.
Ручная команда ждёт завершения текущей фоновой проверки, поэтому нажатие
кнопки не теряется при совпадении с 30-секундным таймером. Ожидание блокировки
ограничено 30 секундами; при длительной операции команда вернёт «busy» и её
можно повторить. Автоматический tick при занятой блокировке пропускается.

Контролируемый перезапуск AdGuard ждёт восстановления доступа к Telegram.
Если AdGuard не восстановился и был активным маршрутом, команда сразу
переключает общую точку на VLESS:

```bash
sudo /usr/local/sbin/mtproxy-failover --restart-adguard
```

Расширенный сетевой статус для управляющего бота:

```bash
/usr/local/sbin/tg-vpn-failover-status --verbose
```

## Развёртывание

На сервере должны быть установлены `sing-box`, `curl`, `python3` и `flock`. Файл подписок создаётся отдельно с правами `0600 root:root`, после чего выполняется `sudo ./install.sh`.

Контроллер устанавливается в `/usr/local/lib/tg-vpn-failover/controller.py`,
`root:root 0644`; wrappers запускают его через системный Python в режиме `-I`.
Дополнительные Python-пакеты не нужны. Подписка загружается только через HTTPS;
URL передаётся curl через stdin и не попадает в список аргументов процесса.

`/run/mtproxy-failover/health.json` содержит время проверки, последний успех
каждого пути и отдельные результаты core/API; секретов в нём нет. Текущий
`tg-vpn-failover-status` пока показывает состояния процессов; использование
health-данных интерфейсом бота — следующий этап обслуживания.

`/etc/sing-box/.mtproxy-transaction.json` — закрытый журнал отката (`0600 root:root`).
Он временно содержит предыдущую конфигурацию и может включать секреты подписки.
Не публикуйте его и не удаляйте при незавершённом применении: следующий tick
или updater под блокировкой восстановит предыдущую конфигурацию. Откат
восстанавливает конфигурацию и состояние процесса; доступность старого внешнего
VPN после этого зависит от провайдера и отражается отдельными health-проверками.

Установщик также отключает оставшиеся от прежней схемы `mtproxy.service`,
`mtproxy-update.timer`, `mtproxy-routing.service` и `redsocks.service`. В текущей схеме
их заменяют `mtg`, `mtproxy-egress` и `mtproxy-failover`.

## Выбор VLESS-узлов

Проверка с этого сервера 2026-09-05 выявила повторные таймауты Telegram TLS
на TCP/Reality-узлах Auto+, тогда как четыре обычных Auto gRPC прошли
повторные проверки. Поэтому приоритет отдан Auto gRPC. Это наблюдение
для данного сервера и подписки, а не общее ограничение VLESS/TCP.

### Отображение проверок

`tg-vpn-failover-status` читает активный маршрут из конфигурации общего egress
и результаты из `health.json`. Успешный VPN требует свежих (не старше 90 секунд)
проверок Core и Bot API через активный upstream и общий SOCKS, а также работающих
процессов. Несовпадение маршрута, пропущенные или устаревшие данные дают предупреждение.
`--verbose` показывает оба upstream, общий SOCKS, последний результат failover
и возраст проверки. Активный таймер сам по себе не доказывает исправность.
`--mtproto` показывает только процесс mtg и локальный порт 443: полноценное
внешнее MTProto-подключение эта команда не проверяет. Статусы не делают сетевых
запросов и не меняют состояние контроллера.
